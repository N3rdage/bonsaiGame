# Architecture

How the web project is organised, the decisions behind it, and the invariants carried over from the GameMaker prototype. For why the rewrite happened, see `docs/ADR-001-typescript-rewrite.md`. For the prototype's own architecture, see `archive/gamemaker/ARCHITECTURE.md`. For deliberately-unsimulated behaviour, see `SIMPLIFICATIONS.md`.

This document describes the project at parity with the prototype: R4, the Phaser rooms and UI, is done, so the web build has the simulation (R2) and the 3D viewer (R3); the title scene with new game, continue, the slot picker and F5/F9 save and load; the day clock, and the shed and the garden drawn from the prototype's sprites and joined by doors, with the garden's source plants giving cuttings, the shed's kiosk selling supplies, its workbench making pots and its planting table planting cuttings; player movement, the HUD, interactables, modal panels, tree sprites and carrying, and the tree inspector with its sub-panels; the tutorial corner panel, its Skip confirmation and Granny's notebook; per-machine settings with the Settings panel; seasonal ambient weather in the garden and dust motes in the shed; and every text in the VT323 pixel font. `e2e/parity.spec.ts` plays that loop end to end in one browser test in landscape, walking on the arrow keys and taking every action by tap, in its own Playwright project (`s22-landscape-parity`) that runs after the four per-step projects: beside them, its 3D viewer render on CI's software GL starved the other worker's walks past their timeouts. What the port deliberately leaves out is noted in the porting map's rows and under "Known rough edges".

## High-level shape

A single-page web game. Vite bundles TypeScript into a static site; Phaser renders the 2D world and UI to a canvas; Three.js renders the 3D tree viewer (pot, trunk, branch, foliage and wire meshes, hotspots, training actions and the pause-while-open lifecycle). The simulation is a set of pure TypeScript modules with no rendering dependency, so it runs identically in the browser, in unit tests, and in any future headless tool.

```
index.html
  src/main.ts            Phaser.Game config, PWA service-worker registration
  src/scenes/            Phaser scenes: boot, title (R4a-2), world (the shed, R4a-1, and the garden, R4c-1)
  src/world/             pure room data, player movement, input and HUD text for the world scene (R4a-1); resolution.ts, the canvas and camera scale
  src/sim/               pure simulation (done, R2): tree, geometry, growth, seasons, scoring, species, styles, training, save
  src/viewer/            Three.js tree viewer: scaffold, pot, trunk/branch/foliage/wire meshes done (R3a-c); hotspots and modes done (R3d-1); toolbar done (R3d-2a); actions done (R3d-2b); lifecycle done (R3d-2c)
  e2e/                   Playwright browser tests
  public/                static assets, PWA icons, staticwebapp.config.json
```

The logical resolution is 480x270, fitted to the window with crisp text over pixel art (see the resolution bullet under "How the scenes are shaped"). This replaces the prototype's room-sized viewports.

## Module rules

- **`src/sim/` imports nothing from Phaser, Three or the DOM.** It takes plain data in and returns plain data out. This is what makes the game testable without a browser and is the main thing the rewrite buys.
- **Scenes own rendering and input, never game rules.** A scene calls into `src/sim/` and draws the result. If a rule needs a number, the number lives in `src/sim/`.
- **Test hook.** Scenes publish a minimal read-only snapshot to `window.__bonsai` (type `BonsaiTestHook` in `src/vite-env.d.ts`). Browser tests assert on it instead of inspecting canvas pixels. It is additive: add fields, never repurpose them.

### How the simulation is shaped

- `src/sim/types.ts` is the whole data model: plain interfaces, JSON-serialisable, no methods. `BonsaiTree.revision` replaces the prototype's `mesh_dirty` flag; every morphology mutation goes through `markDirty` or `addBranch`, and renderers rebuild when the number changes.
- `GameState` carries what the prototype kept in globals (day, money, inventory, trees, next id, tutorial step). Simulation functions take it explicitly and mutate it in place; that is what makes them testable.
- Randomness is injected: `treeDailyTick(tree, state, isolated, rng)` and `advanceDayAllTrees(state, days, rng)` default to `Math.random`, tests pass a constant.
- The prototype's numbers are canon unless a backlog decision says otherwise. Departures so far: the wire safe-bend limit in `training.ts` reads branch girth in centimetres (`60 - (girth / 10) * 20`), where the GML applied the same constants to millimetres, leaving the starter's branches limits of 6 degrees or less (negative above 3 mm) so the penalty was either instant or could never fire (backlog #27, option B). Pruning also renumbers wire and clip history ids, which the prototype left pointing at the wrong branch. Taking a cutting is limited to spring and summer, and pruning to winter (backlog #73; #76, option A); the prototype allowed both all year.
- Saves are versioned. `save.ts` writes version 3 (camelCase; version 2's fields plus `seasonTipShown`) and reads version 3, version 2 (migrated with `seasonTipShown` false, so the first-dormancy tip can still fire once) and the prototype's version 1 through `importPrototypeSave` (also `seasonTipShown` false), which tolerates the trailing NUL byte the prototype wrote, GameMaker's float-typed integers, and the fields older saves lack. Two real prototype saves live in `src/sim/__fixtures__/` as importer tests. Storage is behind a three-method `SaveStorage` interface with an in-memory implementation for tests and a `localStorage` one under `src/platform/`.

### How the scenes are shaped

- `BootScene` (`boot`) is the entry: it creates the one `LocalStorageSaveStorage` the game uses and the `LocalStorageSettingsStorage`, loads the `Settings` once, reads the viewer's `?tree=` and `?season=` test parameters, and starts `TitleScene` (`title`) with them. Every later scene receives the storages, the settings and those overrides through scene data (`src/scenes/sceneData.ts`), so a test could swap the storage; no scene creates its own. The settings are one mutable object shared by the scenes for the session.
- `TitleScene` (`title`, obj_title) shows the title, the version and four buttons: **New Game** (Enter) starts `createNewGameState()` in slot 1 when every slot is empty, otherwise opens the slot picker in "new" mode, where an occupied slot asks to confirm the overwrite (Y/N); **Continue** (C) loads `mostRecentSaveSlot` through `loadGame`, greyed out with no save; **Load Game** (L) opens the picker in "load" mode, where only slots with a save can be picked; **Settings** (S) opens the Settings panel (below) as a title view in the standard `PANEL` box, which Escape or Close returns from. Picker rows (keys 1-3, Escape to cancel) come from the pure `src/world/saveSlots.ts` (`readSlotRows`, the prototype's row text). An unreadable slot counts as occupied: the title says so on arrival, and loading it shows the error and stays on the title. Placeholder-styled like the world; the prototype's 3D hero tree is not ported, and its Quit is not ported at all: a web page has no quit, the browser closes the tab.
- **Phones run landscape only** (pure rule in `src/platform/orientation.ts`, wired in `src/main.ts`): a touch screen with a short side under 500 CSS px held in portrait gets the `#rotate-prompt` DOM overlay, which takes every tap while `game.pause()` stops the whole Phaser loop (day clock, world steps) and `game.input.enabled` is off (Phaser also listens on the window) until it is turned back, and on a phone the first tap on New Game, Continue or Load asks for fullscreen (the Settings toggle's `scale.startFullscreen()`) and, on entering it, a landscape lock, carrying on if refused; the manifest's `orientation` is `landscape`, and tablets and desktops are untouched. Portrait is not a supported layout because the logical canvas is a fixed 16:9 480x270, which on an upright phone fits a strip about a third of the screen tall with text too small to read and tap.
- **Settings** (scr_settings, obj_ui_settings): per-machine, separate from the save slots. The pure `src/platform/settings.ts` has `Settings { fullscreen, weather }`, `DEFAULT_SETTINGS` (`fullscreen: false`, `weather: true`, as `init_settings`), `loadSettings(storage)` (the defaults with only the known boolean keys from storage laid over them; unknown keys, wrong types, malformed JSON or an unreadable store leave the defaults) and `saveSettings`, behind a two-method `SettingsStorage` (`read`, `write`). `LocalStorageSettingsStorage` keeps the JSON under the one key `bonsai.settings`; reads are guarded like the save storage's, and a failed write is swallowed (a toggle must not throw out of a tap) so the value lives on in memory for the session. The prototype's window `scale` (1x-3x) is not ported: the canvas already fits the browser window (see Resolution). The **Settings panel** (pure model `settingsPanel(settings, { available, active })` in `src/world/settingsPanel.ts`, in `PANEL`): `Fullscreen: On|Off`, `Weather effects: On|Off` and Close; a toggle (`toggleSetting` in `src/scenes/settings.ts`) flips the value, applies it, saves and redraws the panel in place. **Fullscreen** calls Phaser's `scale.startFullscreen()` or `stopFullscreen()` inside the tap, the user gesture browsers require, and stores the intended value. The fullscreen element is the whole document (`fullscreenTarget: document.documentElement` in `src/main.ts`), not Phaser's default wrapper around the canvas, because the 3D viewer and the Rename input are DOM siblings of `#game` and would not be rendered outside the fullscreen subtree; `#game` fills the viewport either way, so the FIT refit on `resize` is unchanged. The row shows the live `scale.isFullscreen`, not the stored flag, and both scenes redraw an open panel on the scale manager's `ENTER_FULLSCREEN` and `LEAVE_FULLSCREEN`, so leaving with the browser's Escape shows at once. Nothing is applied at boot: browsers refuse fullscreen outside a gesture, so a stored `fullscreen: true` is not re-applied. Where `document.fullscreenEnabled` is not true (iOS Safari) the row reads `Fullscreen: not available`, grey and not a control. **Weather effects** gates the world's ambient weather (below).
- The world plays one `GameState` (new, or the one loaded) with an **active slot**. Save (the HUD menu or F5) saves it there (`saveGame`, captured so the browser does not reload) and shows `Saved to slot N` for 2 seconds; F9 reloads the slot and restarts the world with it. On an empty or unreadable active slot F9 opens the in-room **Load Game** picker instead, as the prototype's controller did (see the panels below); Close keeps the unsaved game. Escape with the viewer closed returns to the title without saving; there is no autosave. The world creates the `TreeViewer`, owns it until shutdown and publishes the test hook, whose `trees`, `starterScore` and `starterHeightCm` come from the state the world started with, and `day` and `season` from the state at each publish (the day clock moves them).
- **Day clock** (pure `src/world/clock.ts`, the controller's Step_0): `tickClock(state, accumulatorS, deltaS, timeScale)` adds the frame's real seconds times the time scale (`base_time_scale`, 1, or the `?timeScale=` test override read by the boot scene into `ViewerOverrides` through `parseTimeScale`: finite and positive, clamped to `MAX_TIME_SCALE` 10000 so one frame can never loop through unbounded days) and runs `advanceDayAllTrees(state, 1)` once for each whole 300 s taken off, carrying the rest; while `state.paused` nothing accumulates. The world calls it every frame the viewer is closed, modal panels or not (the prototype stopped only on `game_paused`). The accumulator lives on the scene, transient as the prototype's global was: never saved, kept across rooms, reset when the world (re)starts on a new game or a load. A passing day redraws the tree sprites (growth changes their size), rebuilds an open inspector, refreshes the HUD badge and republishes; after the tick it asks `seasonTipFor(state, previousDay)` (pure, `src/sim/seasonTip.ts`) for the first-dormancy tip, which is due when the day crossed into a new season, a tree the player owns (not sold) is dormant in it (`seasonGrowthMultiplier(species.seasonsActive, season) <= 0`; today that is the juniper and the maple in winter) and `state.seasonTipShown` is false: the scene then sets the flag (saved, so the tip fires once a game) and holds the text for the corner panel; display revenue above 0 shows as the toast `Display revenue: +$N` (the prototype only debug-printed it). The debug keys F1 (skip 7 days on tree 0; the inspector's `Skip 7d` does it) and F2 (advance the world 7 days) are not ported: every shipped key needs a tap control, and `?timeScale=` lets the browser tests see days pass.
- **Rooms and doors** (pure `src/world/shedRoom.ts` and `gardenRoom.ts`; `ROOMS` maps a `RoomKey`, `shed` or `garden`, to its `Room`): the world draws whatever room it is given (from sprites; see the assets bullet below) and keeps it in `room`, which the player's step, the tree sprites, Put down, the dimmers and the hook's `room` all read. A door is a prop with a `target` (`{ room, x, y }`, obj_door's `target_room`, `target_x`, `target_y` from the instance creation code, halved): the shed's `To Garden` (prototype top-left origin (464, 416), 32x32, so centred at (240, 216), 16x16, in the bottom wall) lands at (50, 225) in the garden, the garden's `Back to Shed` (prototype top-left origin (16, 440), so centred at (16, 228)) at (240, 190) on the shed floor just above the shed door, 26 px from its centre and so just out of its 20 px reach (the prototype measured to the door's top-left origin, which put the landing spot in reach). Interacting with a door swaps the room in place: the old room's parts are destroyed, the new one drawn, the player moved to the target (facing kept, as the prototype's persistent player did), with no fade. The garden (`rm_garden_back`) is 480x270 with the background `0x30502c` (ABGR `0xff2c5030`, under the floor tiles) and the controller's fence ring as 16 px collision bands, the left one broken by the doorway at y 208..240 (prototype 416..480). A new or loaded game starts in the shed.
- **Source plants** (obj_source_plant; the rule in pure `src/sim/sourcePlant.ts`): three 24x24 props centred at the halved instance positions, `juniper` (140, 90), `maple` (260, 80) and `pine` (380, 100), each drawn as its species' frame of `spr_source_plant` (unlabelled, as in the prototype), prompt `Take Cutting`. `takeCutting(state, plant, speciesKey)` returns the toast, with the prototype's strings: `This plant is recovering - ready on day N` while `regrowDay` is ahead; `<Display name> can't be grown from cuttings - try seeds` for a species without `cutting` in its `propagation` (maple, pine); `Cuttings are taken in spring or summer - try again on day N` outside `CUTTING_SEASONS`, N the first day of the next spring (`nextCuttingSeasonDay`; backlog #73, 2e-a); else one `cutting_<species>` into the inventory, `tutorialAdvanceIf(state, TUTORIAL_TAKE_CUTTING)`, and `Took a <Display name> cutting  (N in inventory)` (two spaces, as in the GML), the third cutting adding ` - plant now recovering` and setting `regrowDay` 14 days ahead. The counters (`SourcePlantState`: `cuttingsTaken`, `regrowDay`) are kept per plant for the current visit only and reset on every room entry, as the prototype's instances were recreated on each `room_goto`; they are never saved.
- **Weather** (scr_weather, obj_weather; pure `src/world/weather.ts`): eye candy derived from `seasonForDay(state.day)`, nothing persisted. `weatherProfile(season, indoor)` gives the shed's dust motes (`motes`, 10) whatever the season, else spring `petals` 28, summer `fireflies` 14, autumn `leaves` 24, winter `snow` 48, with the prototype's counts, alphas and colours; every px distance, px-per-step speed (fall, wind), sway amplitude and size is halved, and the angular speeds (sway, spin, glow phase, degrees per step) are verbatim. `createParticles(profile, area, rng)` scatters the field over the area (Create; `rng` injected, `Math.random` by default), `stepParticles` applies the Step event (fall, wind, sway, spin, glow at half the sway speed, toroidal wrap over the area plus a 12 px margin) and `particleDraw` gives each particle's swayed and bobbed position, glow-pulsed alpha (`0.55 + 0.45 sin(gph)`) and shapes (circles; a firefly's halo at 2x size and 0.35 alpha under its core; rotated quads, petals 0.5w x 0.8h and leaves 0.55w x 1h). The area is the whole room in the garden and the halved wall ring (80, 48)..(384, 208) in the shed (`isIndoor`). The world draws it into one `Graphics` at depth 9000, above the room, props, trees and player (depth at most 270) and below the HUD (10000) and modal panels, as the prototype's -1000 sat in front of the instance layer and behind the GUI. It steps once per fixed step, modal panels or not, and redraws after stepping; it rebuilds on room entry (the prototype's instance was per room) and after a day tick that changes the season. While the `weather` setting is off there is no field (nothing stepped, the Graphics cleared); the Settings panel's toggle clears it, and turning it back on respawns a fresh field (the old particles are not kept, so nothing freezes and resumes). The Graphics is hidden under the viewer, and the title has none.
- **Resolution.** Every layout number, room distance and hook coordinate is in logical 480x270 units. The canvas backing is sized to the device pixels of the fitted 16:9 display (`src/world/resolution.ts`, applied in `src/main.ts` and re-applied on every resize), and each scene's camera is zoomed by that factor (`fitCamera` in `src/scenes/crisp.ts`), so sprites and shapes keep their chunky logical scale with nearest-neighbour filtering (`pixelArt: true`) while every Text renders at the same resolution (`crispText`) and its glyphs land on native pixels; the device pixel ratio enters the Phaser layer nowhere else, and the Three.js viewer is a separate DOM canvas with its own pixel-ratio handling. Every Text is in the VT323 pixel font (`@fontsource/vt323`, SIL OFL 1.1; monospace, 0.4 em advance, 1 em line height): `BootScene.preload` loads the package's latin woff2 with Phaser's `load.font` before the title is created, so no text ever draws in the fallback and jumps, and Workbox precaches the file (`woff2` in `globPatterns`); `src/scenes/textStyle.ts` is the one place the family is named (`FONT_FAMILY`, `labelStyle(ui)` and `bodyStyle(ui)`, `fontLoaded` for the hook), every scene and panel composes its styles from it, and the Rename input shares it. The layout constants measured in characters were pinned against the browser `monospace` (about 0.6 em), which stays the CSS fallback and is wider, so they stand as upper bounds. **UI scale rule** (pure `src/world/uiScale.ts`, backlog #87): the scale is the fitted canvas's CSS px per logical px, `cssPerLogical(w, h) = min(w / 480, h / 270)` (about 1.42 on the S22 in landscape, 2.67 at 1280x720), and `uiMetrics(scale, touch)` gives in logical px `hit` = `ceil(minTap / scale)` (`MIN_TAP_CSS_TOUCH` 44 on a touch screen, `MIN_TAP_CSS_POINTER` 24 otherwise, WCAG 2.5.8), `label` = `max(8, ceil(14 / scale))` and `body` = `max(10, ceil(14 / scale))` (`MIN_TEXT_CSS` 14); pinned as `PHONE_UI` `{ hit: 31, label: 10, body: 10 }` and `DESKTOP_UI` `{ hit: 9, label: 8, body: 10 }`, so the desktop layout is unchanged by construction. `hitRect(bounds, hit)` grows a control's text box to at least `hit` square round its centre, then shifts it inside the canvas (an edge button grows inward); `setHitArea` in `src/scenes/crisp.ts` gives it to Phaser's `setInteractive` in the Text's local space, and every tappable Text in the world and on the title gets its area that way. Both scenes read the metrics at `create` (`sceneUi`: `scale.displaySize` and `device.input.touch`; the world's own texts, the prompt and tree labels, at the world camera's zoom on top) and on every resize re-read `hit` only: the HUD's buttons (and the title's) get their hit areas re-applied, an open panel keeps its layout until it is next opened, and text sizes stay until the scene restarts. Control rows are at least `hit` apart: `fitRows(model, ui)` in `panels.ts` (below), the inspector's `inspectorPanel(tree, state, ui)`, the menu's `menuItems(carrying, ui)`, the tutorial box, and the title's menu (26 px pitch) and slot picker (24 px, Cancel at least 200), widened to `hit`.

### How the viewer is shaped

- A separate WebGL canvas (`#viewer`) sits fixed over the Phaser canvas and is shown only while the viewer is open.
- The camera is plain yaw/pitch/distance data in the pure `camera.ts`; the world is z-up, as in the prototype.
- Handedness: the prototype's look-at was left-handed, so the viewer mirrors the world's y axis (`toViewerSpace` in `camera.ts`, a y-flipped mesh group in `TreeViewer.ts`). Screen-right at yaw 45 is world (-1,-1,0), as in the prototype. Hotspot projection goes through the same helper.
- Rendering is on demand (one frame per open, resize or input change), never a loop, without MSAA, so a still view is a deterministic screenshot.
- Pure array builders (`potGeometry.ts`) feed Three.js `BufferGeometry`, so mesh shape is unit-tested in Node. `threeCamera.ts` uses only Three's math classes and is unit-tested too; only `TreeViewer.ts` needs WebGL.
- The tree mesh comes from the pure `treeMesh.ts`, which reads shape only from `trunkFrames`, `branchPoint` and the `*FrameAt` lookups. `TreeViewer.ts` keeps it as one `Mesh` in the mirrored group beside the pot and rebuilds it before a render only when `tree.revision` has changed since the last build.
- Wire is part of the bark mesh, as in the prototype: right after a wired branch's bark, `treeMesh.ts` appends a copper helix around the branch and a 1.5-turn anchor wrap around the trunk at its base, ending on the branch's side. Every sample takes its frame from `branchFrameAt` or `trunkFrameAt`, so the coil follows the bent branch and the anchor a leaning trunk, and each tube ring is an oriented ring perpendicular to the helix tangent. Gauge and pitch scale with branch girth and bend.
- Foliage comes from the pure `foliageMesh.ts`: a seeded cluster of crossed, textured quads at each branch tip above 30% of trunk height, tinted by the species' seasonal colour through the vertex colour. The seed is `tree.id * 1000 + branch.id` (mulberry32 in `seededRandom.ts`), so rebuilds never reroll the leaves. `TreeViewer.ts` draws it as a second `Mesh` with its own material (sprite map, alpha test 0.5, no culling).
- The season is an input, never derived: `open(tree, season, state)` and `setSeason(season)`. The viewer reads the game state's day only for wire-age captions and prune mode's `Prune: requires winter` note, never for the displayed season: the prune gate follows the game's day even when `?season=` overrides what is drawn. Foliage rebuilds before a render when `tree.revision` or the season differs from what it was built with; bark rebuilds on `revision` only.
- Colour space: the renderer outputs `LinearSRGBColorSpace` so palette bytes pass through untouched, and the foliage sprite (`foliage.png`, the prototype's `spr_foliage` copied byte for byte) loads with `NoColorSpace`, nearest filtering and no mipmaps for the same reason. The map is bound when it finishes loading; `foliageReady` on the test hook says when.
- Interaction state is plain data in the pure `hotspots.ts`: mode (`view`, `wire`, `clip`, `prune`, keys V/W/C/P), wire action, bend direction and the wired/unwired filters, reset on every `open`. `hotspotWorldPoints(tree, ui)` gives the hotspots for that state in world space (branch ones at 70% along each branch, trunk ones at 20-80% of the trunk in wire + bend) with the prototype's filters, labels and colours. Nothing in it mutates the tree.
- Hotspots are a DOM overlay (`#viewer-hotspots`, one `button.hotspot` each), not drawn in WebGL: tests read their positions from the hook and the DOM, they get hover and focus for free, and `e2e/screenshot.css` hides them so baselines stay the WebGL frame. `TreeViewer.ts` lays them out again after every rendered frame, so they follow the camera. Each button's hit circle is the prototype's 16 px radius. The overlay sits above the canvas, so a press on a hotspot never starts a camera drag.
- Clicking a hotspot acts through `src/sim/training.ts`: clip mode calls `clipBranch(tree, state, id, 1)` in any season, prune mode `pruneBranch`, which refuses unless `pruneCheck` is `ok` (winter only, `PRUNE_SEASONS`; backlog #76, option A; the hotspots stay and the help line reads `Prune: requires winter`, as an out-of-stock wire's click is refused and the help says `(out)`), wire + bend `applyWire` with the targets from `branchBendTarget` (one 15 degree step on `bend` for left/right or `bendV` for up/down, its sign from `branchBendSign` with the hotspots' own projection), and a trunk hotspot `wireTrunk` at `t * trunk height` toward `trunkBendWorldAngle(bendDir, yaw)`. Wire + remove opens the confirmation (`#viewer-modal`: the pure `modal.ts` holds the prototype's sizes, colours and strings, `ViewerModal.ts` draws it); its Remove calls `removeWire`. While it is open its dim takes every pointer event, the toolbar and hotspots are inert, Escape closes the modal (not the viewer) and other keys do nothing. Hotspot clicks are ignored while a frame is pending, so a second click before the buttons are rebuilt cannot hit a branch a prune just renumbered. Apart from `state.paused` (below), the viewer never writes the tree or state itself: the sim functions do, consuming wire from the inventory and refusing when there is none (the help line then reads `(out)`); a successful action bumps `tree.revision`, so the next frame rebuilds the mesh and the toolbar.
- The toolbar is DOM too: `#viewer-toolbar` (tree info, View/Wire/Clip/Prune and Exit buttons, and in wire mode the action, bend-direction and show sub-row) and `#viewer-help` (the bottom help lines, with the wire stock in wire mode and, in prune mode outside winter, `Prune: requires winter` above the camera line). The pure `toolbar.ts` builds a plain-data model from the tree, interaction state, wire stock and day, holds the prototype's sizes, colours and strings, and gives the wire-age caption under wired hotspots; `ViewerToolbar.ts` draws it after every frame (skipping an unchanged model) and reports clicks to `TreeViewer`'s setters and `close()`. `open(tree, season, state)` takes the `GameState` so it can read the wire stock and day and pass it to the training functions. Mode and camera keys ignore Ctrl, Meta and Alt chords; Escape closes the viewer unless the confirmation is open.
- The viewer pauses the simulation, as the prototype did with `global.game_paused`: `open` sets `state.paused = true` (only once WebGL is available) and `close` (Escape, the Exit button, or the owner) sets it back to false on the state it was opened with. `advanceDayAllTrees` is a no-op while paused. The flag is transient: `serializeState` never writes it and every load starts unpaused. `paused` on the test hook mirrors it.
- `projection.ts` maps a world point to CSS px with Three's math classes only (unit-tested in Node). It goes through `toViewerSpace`, as the handedness rule demands, and drops points behind the camera or outside the near/far range.
- The top strip (60 px, 110 px in wire mode, the prototype's toolbar and wire sub-row) never starts a drag; on a phone the DOM toolbar wraps taller and takes the press itself. Wheel zoom works anywhere over the canvas; pinch zoom wherever the first finger could start a drag; the camera buttons wherever they are drawn.
- Pinch zoom: `pinchZoom(camAtPinchStart, startPx, nowPx)` in `camera.ts` moves `distance` by the change in finger distance over `PINCH_PX_PER_NOTCH` (20 px) wheel steps, continuously, clamped to the wheel's limits, and never touches yaw, pitch or target. `TreeViewer.ts` tracks the pointers down on the canvas: one starts a drag (below the top strip, as before); a second landing during the drag ends it and starts a pinch from the camera at that moment; moves during the pinch only zoom; lifting either finger ends the pinch, and the finger left down needs a new press to drag. A third finger is ignored. Opening the confirmation or closing the viewer cancels a drag or pinch.
- Camera buttons (`#viewer-camera`, built once by `ViewerToolbar.ts`): zoom in (`+`), zoom out (`−`) and reset (`R`), a column at the right edge, vertically centred, sized by `CAMERA_BUTTON_SIZE` (36), `CAMERA_BUTTON_GAP` (8) and `CAMERA_BUTTONS_RIGHT` (20) in `toolbar.ts`. Zoom is one wheel step (`zoomCamera` by -1 or +1), reset is `resetCamera`, as the wheel and R. Inert with the toolbar under the confirmation; hidden by `e2e/screenshot.css` so baselines stay the WebGL frame.
- On a viewport narrower than `SUBROW_ONE_LINE_WIDTH` (830 px, the bend sub-row on one line at the prototype's 24 px group separator) the sub-row's groups sit `SUBROW_SEPARATOR_NARROW` (12 px) apart (`subRowSeparator(viewportWidth)` in `toolbar.ts`), so a phone in landscape (824 px wide) keeps the wire toolbar at 110 px instead of wrapping over the top of the tree. Exit sits in the mode buttons' flex flow (16 px after Prune, as before), so on a narrow viewport it wraps beside Prune rather than taking a row of its own. Branch hotspots stack above trunk hotspots, so where the two overlap on a short viewport a tap takes the branch. The help lines and the modal are unchanged at every size; the S22 Ultra in landscape (`s22-landscape`) shows the tree and the whole pot between them in every mode.
- The direction helpers `trunkBendWorldAngle` (screen direction to a world bend angle at the current yaw) and `branchBendSign` (which bend sign moves a branch tip the chosen way on screen, found by projecting a perturbed copy) are pure and take the projector as an argument; the wire actions use them.
- Screenshot tests open fixture trees (`viewerFixtures.ts`, grown through `src/sim` actions) with a `?tree=<cutting|bent|cascade|maple|wired|fancy>` URL parameter, and choose the viewer's season with `?season=<spring|summer|autumn|winter>` (default: the game's season), both read by the boot scene; the tests start a new game from the title with Enter and open the viewer with V in the world. The parameters stay until R4's interactables give a real way to pick a tree.
- Screenshot baselines live in `e2e/__screenshots__/` and are regenerated on Linux with `npx playwright test --update-snapshots=all`.

## Invariants carried over

These were the hard-won rules of the prototype. Each names where it will live in the web project.

- **The tree model is the single source of truth.** 2D sprite and 3D mesh both derive from it. No display state stored separately from morphology. (`src/sim/tree.ts`)
- **Real units.** Trunk height in cm, girth in mm. Scaling for display happens in the viewer only. (`src/sim/`, `src/viewer/`)
- **Scoring is derived, never persisted.** Recompute on demand from morphology, style and vitality. (`src/sim/scoring.ts`)
- **Species and styles are data.** Keyed records, looked up by key; trees store the key. (`src/sim/species.ts`, `src/sim/styles.ts`)
- **Seasons are a pure function of the game day.** 28-day seasons, year starts in spring on day 1, nothing persisted. A new game starts on day 0 as the prototype did; `seasonForDay` treats it as day 1. (`src/sim/seasons.ts`)
- **All growth goes through the season multipliers.** `seasonGrowthMultiplier` returns 0 for dormancy; any path that adds height or girth must consult it. Fertilising refuses when it is 0. Season also gates the non-growth paths: repotting is spring-only, taking a cutting is limited to `CUTTING_SEASONS` (spring and summer), and pruning (removing a branch) to `PRUNE_SEASONS` (winter) through `pruneCheck`, while clipping stays year-round. (`src/sim/seasons.ts`, `src/sim/growth.ts`, `src/sim/sourcePlant.ts`, `src/sim/training.ts`)
- **Trunk and branch shape come from one curve helper each**, shared by the mesh builder, hotspot UI and style scorers, so what you see is what you score. (`src/sim/geometry.ts`)
- **Mesh rebuilds are triggered by a revision counter** bumped by every morphology mutation. (`tree.revision`, read by `src/viewer/`)
- **Consumables are really consumed.** Wire, fertiliser and pots are decremented by the action that uses them, gated on availability. (`src/sim/inventory.ts`)
- **Fertiliser is timed.** The item is consumed; the effect lives on the tree until a day threshold. (`src/sim/growth.ts`)
- **Location is a tagged string**, not an enum: a room name, `inventory`, `sold`, or `displayed:<pedestal-key>`. (`src/sim/tree.ts`)
- **Tutorial state is one step counter** advanced idempotently from gameplay call sites. (`src/sim/tutorial.ts`)
- **The 3D viewer pauses the simulation.** `state.paused` (the prototype's `global.game_paused`) is true while the viewer is open; the day advance does nothing while it is. Transient, never saved. (`src/sim/world.ts`, `src/viewer/TreeViewer.ts`)
- **Saves carry a version** and old shapes migrate forward. Prototype saves import one way. (`src/sim/save.ts`)

## Build, test, deploy

- **Gates** (`npm run check`, mirrored in `.github/workflows/ci.yml`): ESLint strict type-checked, Prettier, `tsc --noEmit`, Vitest with coverage, Vite build, then Playwright against the built output. The whole suite runs in two profiles, `chromium` (desktop Chrome, 1280 x 720) and `s22-landscape` (Drew's Samsung Galaxy S22 Ultra in Chrome at its default FHD+ display mode, 824 x 384 CSS px at scale factor 2.8125), with epic #8's loop in `s22-landscape-parity` after them. The two phone-portrait profiles, `mobile` (Pixel 7) and `s22-portrait` (384 x 824), run only `e2e/orientation.spec.ts`, because a phone held upright gets the rotate prompt and nothing else: that spec checks the prompt and the pause under it there, and on desktop that turning 384 x 824 to 824 x 384 at runtime refits the world canvas and re-renders the viewer without a reload.
- **Tap parity.** The browser tests drive the game through `e2e/drive.ts`. On the S22 projects (`tapRoute: true`) it reaches every action through its visible control by touch; elsewhere through its key or a click. So the suite proves tap parity on the phone and keeps the shortcuts tested on desktop. Gestures (drags, pinch) are the same everywhere; movement keys and the few tests of key handling itself stay keys on every project.
- **Build version.** `vite.config.ts` defines `__APP_VERSION__` as `yyyy.mm.dd.build` through the pure `src/buildVersion.ts`: the UTC date of the commit being built (`git log -1 --format=%cI`) and `GITHUB_RUN_NUMBER` (`0` locally), so it depends only on the commit and the CI run, never on when the build ran; `package.json`'s semver stays the package's own. `__APP_COMMIT__` is `GITHUB_SHA` or `git rev-parse HEAD` (`unknown` without either, with the date `0000.00.00`), and `__APP_COMMIT_URL__` its GitHub page, which the title's version line opens in a new tab.
- **PWA.** `vite-plugin-pwa` generates the manifest and a Workbox service worker that precaches the build. The precache size cap is raised because Phaser alone exceeds the default.
- **Hosting.** Azure Static Web Apps. `public/staticwebapp.config.json` sets SPA fallback, security headers and cache policy. `.github/workflows/deploy-swa.yml` deploys `main` to production and each PR to a preview environment, and removes the preview on close. The deploy token lives in a repository secret; without it the workflow verifies the build and skips.
- **Security.** Gitleaks on every push and PR; CodeQL via the repository's default setup; Dependabot for npm and Actions, grouped weekly.
