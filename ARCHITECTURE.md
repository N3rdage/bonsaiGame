# Architecture

How the web project is organised, the decisions behind it, and the invariants carried over from the GameMaker prototype. For why the rewrite happened, see `docs/ADR-001-typescript-rewrite.md`. For the prototype's own architecture, see `archive/gamemaker/ARCHITECTURE.md`. For deliberately-unsimulated behaviour, see `SIMPLIFICATIONS.md`.

This document describes the project as it stands after slice R4d-3 (simulation done; the 3D viewer done in R3; the day clock, and the shed and the garden as placeholder rooms joined by doors, with the garden's source plants giving cuttings, the shed's kiosk selling supplies, its workbench making pots and its planting table planting cuttings; player movement, the HUD, interactables, modal panels, tree sprites and carrying, and the tree inspector with its sub-panels; the tutorial corner panel, its Skip confirmation and Granny's notebook; the title scene with new game, continue, the slot picker and F5/F9 save and load; per-machine settings with the Settings panel; seasonal ambient weather in the garden and dust motes in the shed) and the shape the port is heading toward: the rest of the Phaser rooms and UI (R4). Sections marked *planned* describe modules that do not exist yet.

## High-level shape

A single-page web game. Vite bundles TypeScript into a static site; Phaser renders the 2D world and UI to a canvas; Three.js renders the 3D tree viewer (pot, trunk, branch, foliage and wire meshes, hotspots, training actions and the pause-while-open lifecycle). The simulation is a set of pure TypeScript modules with no rendering dependency, so it runs identically in the browser, in unit tests, and in any future headless tool.

```
index.html
  src/main.ts            Phaser.Game config, PWA service-worker registration
  src/scenes/            Phaser scenes: boot, title (R4a-2), world (the shed, R4a-1, and the garden, R4c-1), more rooms and UI (planned)
  src/world/             pure room data, player movement, input and HUD text for the world scene (R4a-1); resolution.ts, the canvas and camera scale
  src/sim/               pure simulation (done, R2): tree, geometry, growth, seasons, scoring, species, styles, training, save
  src/viewer/            Three.js tree viewer: scaffold, pot, trunk/branch/foliage/wire meshes done (R3a-c); hotspots and modes done (R3d-1); toolbar done (R3d-2a); actions done (R3d-2b); lifecycle done (R3d-2c)
  e2e/                   Playwright browser tests
  public/                static assets, PWA icons, staticwebapp.config.json
```

The logical resolution is 480x270, fitted to the window with crisp text over pixel art (see the resolution bullet under "How the scenes are shaped"). This replaces the prototype's room-sized viewports.

## Module rules

- **`src/sim/` imports nothing from Phaser, Three or the DOM.** It takes plain data in and returns plain data out. This is what makes the game testable without a browser and is the main thing the rewrite buys.
- **Scenes own rendering and input, never game rules.** A scene calls into `src/sim/` and draws the result. If a rule needs a number, the number lives in `src/sim/`.
- **Test hook.** Scenes publish a minimal read-only snapshot to `window.__bonsai` (type `BonsaiTestHook` in `src/vite-env.d.ts`). Browser tests assert on it instead of inspecting canvas pixels. It is additive: add fields, never repurpose them.

### How the simulation is shaped

- `src/sim/types.ts` is the whole data model: plain interfaces, JSON-serialisable, no methods. `BonsaiTree.revision` replaces the prototype's `mesh_dirty` flag; every morphology mutation goes through `markDirty` or `addBranch`, and renderers rebuild when the number changes.
- `GameState` carries what the prototype kept in globals (day, money, inventory, trees, next id, tutorial step). Simulation functions take it explicitly and mutate it in place; that is what makes them testable.
- Randomness is injected: `treeDailyTick(tree, state, isolated, rng)` and `advanceDayAllTrees(state, days, rng)` default to `Math.random`, tests pass a constant.
- The prototype's numbers are canon unless a backlog decision says otherwise. Departures so far: the wire safe-bend limit in `training.ts` reads branch girth in centimetres (`60 - (girth / 10) * 20`), where the GML applied the same constants to millimetres, leaving the starter's branches limits of 6 degrees or less (negative above 3 mm) so the penalty was either instant or could never fire (backlog #27, option B). Pruning also renumbers wire and clip history ids, which the prototype left pointing at the wrong branch.
- Saves are versioned. `save.ts` writes version 2 (camelCase) and reads both version 2 and the prototype's version 1 through `importPrototypeSave`, which tolerates the trailing NUL byte the prototype wrote, GameMaker's float-typed integers, and the fields older saves lack. Two real prototype saves live in `src/sim/__fixtures__/` as importer tests. Storage is behind a three-method `SaveStorage` interface with an in-memory implementation for tests and a `localStorage` one under `src/platform/`.

### How the scenes are shaped

- `BootScene` (`boot`) is the entry: it creates the one `LocalStorageSaveStorage` the game uses and the `LocalStorageSettingsStorage`, loads the `Settings` once, reads the viewer's `?tree=` and `?season=` test parameters, and starts `TitleScene` (`title`) with them. Every later scene receives the storages, the settings and those overrides through scene data (`src/scenes/sceneData.ts`), so a test could swap the storage; no scene creates its own. The settings are one mutable object shared by the scenes for the session.
- `TitleScene` (`title`, obj_title) shows the title, the version and four buttons: **New Game** (Enter) starts `createNewGameState()` in slot 1 when every slot is empty, otherwise opens the slot picker in "new" mode, where an occupied slot asks to confirm the overwrite (Y/N); **Continue** (C) loads `mostRecentSaveSlot` through `loadGame`, greyed out with no save; **Load Game** (L) opens the picker in "load" mode, where only slots with a save can be picked; **Settings** (S) opens the Settings panel (below) as a title view in the standard `PANEL` box, which Escape or Close returns from. Picker rows (keys 1-3, Escape to cancel) come from the pure `src/world/saveSlots.ts` (`readSlotRows`, the prototype's row text). An unreadable slot counts as occupied: the title says so on arrival, and loading it shows the error and stays on the title. Placeholder-styled like the world; the prototype's 3D hero tree is not ported yet, and its Quit is not ported at all: a web page has no quit, the browser closes the tab.
- **Settings** (scr_settings, obj_ui_settings): per-machine, separate from the save slots. The pure `src/platform/settings.ts` has `Settings { fullscreen, weather }`, `DEFAULT_SETTINGS` (`fullscreen: false`, `weather: true`, as `init_settings`), `loadSettings(storage)` (the defaults with only the known boolean keys from storage laid over them; unknown keys, wrong types, malformed JSON or an unreadable store leave the defaults) and `saveSettings`, behind a two-method `SettingsStorage` (`read`, `write`). `LocalStorageSettingsStorage` keeps the JSON under the one key `bonsai.settings`; reads are guarded like the save storage's, and a failed write is swallowed (a toggle must not throw out of a tap) so the value lives on in memory for the session. The prototype's window `scale` (1x-3x) is not ported: the canvas already fits the browser window (see Resolution). The **Settings panel** (pure model `settingsPanel(settings, { available, active })` in `src/world/settingsPanel.ts`, in `PANEL`): `Fullscreen: On|Off`, `Weather effects: On|Off` and Close; a toggle (`toggleSetting` in `src/scenes/settings.ts`) flips the value, applies it, saves and redraws the panel in place. **Fullscreen** calls Phaser's `scale.startFullscreen()` or `stopFullscreen()` inside the tap, the user gesture browsers require, and stores the intended value; the row shows the live `scale.isFullscreen`, not the stored flag, and both scenes redraw an open panel on the scale manager's `ENTER_FULLSCREEN` and `LEAVE_FULLSCREEN`, so leaving with the browser's Escape shows at once. Nothing is applied at boot: browsers refuse fullscreen outside a gesture, so a stored `fullscreen: true` is not re-applied. Where `document.fullscreenEnabled` is not true (iOS Safari) the row reads `Fullscreen: not available`, grey and not a control. **Weather effects** gates the world's ambient weather (below).
- The world plays one `GameState` (new, or the one loaded) with an **active slot**. Save (the HUD menu or F5) saves it there (`saveGame`, captured so the browser does not reload) and shows `Saved to slot N` for 2 seconds; F9 reloads the slot and restarts the world with it. On an empty or unreadable active slot F9 opens the in-room **Load Game** picker instead, as the prototype's controller did (see the panels below); Close keeps the unsaved game. Escape with the viewer closed returns to the title without saving; there is no autosave. The world creates the `TreeViewer`, owns it until shutdown and publishes the test hook, whose `trees`, `starterScore` and `starterHeightCm` come from the state the world started with, and `day` and `season` from the state at each publish (the day clock moves them).
- **Day clock** (pure `src/world/clock.ts`, the controller's Step_0): `tickClock(state, accumulatorS, deltaS, timeScale)` adds the frame's real seconds times the time scale (`base_time_scale`, 1, or the `?timeScale=` test override read by the boot scene into `ViewerOverrides` through `parseTimeScale`: finite and positive, clamped to `MAX_TIME_SCALE` 10000 so one frame can never loop through unbounded days) and runs `advanceDayAllTrees(state, 1)` once for each whole 300 s taken off, carrying the rest; while `state.paused` nothing accumulates. The world calls it every frame the viewer is closed, modal panels or not (the prototype stopped only on `game_paused`). The accumulator lives on the scene, transient as the prototype's global was: never saved, kept across rooms, reset when the world (re)starts on a new game or a load. A passing day redraws the tree sprites (growth changes their size), rebuilds an open inspector, refreshes the HUD badge and republishes; display revenue above 0 shows as the toast `Display revenue: +$N` (the prototype only debug-printed it). The debug keys F1 (skip 7 days on tree 0; the inspector's `Skip 7d` does it) and F2 (advance the world 7 days) are not ported: every shipped key needs a tap control, and `?timeScale=` lets the browser tests see days pass.
- **Rooms and doors** (pure `src/world/shedRoom.ts` and `gardenRoom.ts`; `ROOMS` maps a `RoomKey`, `shed` or `garden`, to its `Room`): the world draws whatever room it is given (floor colour, wall strips, labelled prop rectangles) and keeps it in `room`, which the player's step, the tree sprites, Put down, the dimmers and the hook's `room` all read. A door is a prop with a `target` (`{ room, x, y }`, obj_door's `target_room`, `target_x`, `target_y` from the instance creation code, halved): the shed's `To Garden` (232, 208) lands at (50, 225) in the garden, the garden's `Back to Shed` (prototype top-left origin (16, 440), 32x32, so centred at (16, 228), 16x16) at (240, 190) in the shed, within reach of the shed door as in the prototype. Interacting with a door swaps the room in place: the old room's parts are destroyed, the new one drawn, the player moved to the target (facing kept, as the prototype's persistent player did), with no fade. The garden (`rm_garden_back`) is 480x270 with the floor `0x30502c` (its background, ABGR `0xff2c5030`) and the controller's fence ring as thin edge strips, the left one broken by the doorway at y 208..240 (prototype 416..480). A new or loaded game starts in the shed.
- **Source plants** (obj_source_plant; the rule in pure `src/sim/sourcePlant.ts`): three 24x24 green props centred at the halved instance positions, `juniper` (140, 90), `maple` (260, 80) and `pine` (380, 100), labelled with the species display name, prompt `Take Cutting`. `takeCutting(state, plant, speciesKey)` returns the toast, with the prototype's strings: `This plant is recovering - ready on day N` while `regrowDay` is ahead; `<Display name> can't be grown from cuttings - try seeds` for a species without `cutting` in its `propagation` (maple, pine); else one `cutting_<species>` into the inventory, `tutorialAdvanceIf(state, TUTORIAL_TAKE_CUTTING)`, and `Took a <Display name> cutting  (N in inventory)` (two spaces, as in the GML), the third cutting adding ` - plant now recovering` and setting `regrowDay` 14 days ahead. The counters (`SourcePlantState`: `cuttingsTaken`, `regrowDay`) are kept per plant for the current visit only and reset on every room entry, as the prototype's instances were recreated on each `room_goto`; they are never saved.
- **Weather** (scr_weather, obj_weather; pure `src/world/weather.ts`): eye candy derived from `seasonForDay(state.day)`, nothing persisted. `weatherProfile(season, indoor)` gives the shed's dust motes (`motes`, 10) whatever the season, else spring `petals` 28, summer `fireflies` 14, autumn `leaves` 24, winter `snow` 48, with the prototype's counts, alphas and colours; every px distance, px-per-step speed (fall, wind), sway amplitude and size is halved, and the angular speeds (sway, spin, glow phase, degrees per step) are verbatim. `createParticles(profile, area, rng)` scatters the field over the area (Create; `rng` injected, `Math.random` by default), `stepParticles` applies the Step event (fall, wind, sway, spin, glow at half the sway speed, toroidal wrap over the area plus a 12 px margin) and `particleDraw` gives each particle's swayed and bobbed position, glow-pulsed alpha (`0.55 + 0.45 sin(gph)`) and shapes (circles; a firefly's halo at 2x size and 0.35 alpha under its core; rotated quads, petals 0.5w x 0.8h and leaves 0.55w x 1h). The area is the whole room in the garden and the halved wall ring (80, 48)..(384, 208) in the shed (`isIndoor`). The world draws it into one `Graphics` at depth 9000, above the room, props, trees and player (depth at most 270) and below the HUD (10000) and modal panels, as the prototype's -1000 sat in front of the instance layer and behind the GUI. It steps once per fixed step, modal panels or not, and redraws after stepping; it rebuilds on room entry (the prototype's instance was per room) and after a day tick that changes the season. While the `weather` setting is off there is no field (nothing stepped, the Graphics cleared); the Settings panel's toggle rebuilds or clears it in place. The Graphics is hidden under the viewer, and the title has none.
- **Resolution.** Every layout number, room distance and hook coordinate is in logical 480x270 units. The canvas backing is sized to the device pixels of the fitted 16:9 display (`src/world/resolution.ts`, applied in `src/main.ts` and re-applied on every resize), and each scene's camera is zoomed by that factor (`fitCamera` in `src/scenes/crisp.ts`), so sprites and shapes keep their chunky logical scale with nearest-neighbour filtering (`pixelArt: true`) while every Text renders at the same resolution (`crispText`) and its glyphs land on native pixels; the device pixel ratio enters the Phaser layer nowhere else, and the Three.js viewer is a separate DOM canvas with its own pixel-ratio handling.
- **Halved coordinates.** Prototype rooms are 960x540 and the logical canvas is 480x270, so every prototype position and distance halves (`fromPrototype` in `src/world/shedRoom.ts`, pinned in its tests). The player starts at (240, 135); the clamp is 4 px from the edges; speed is 1.25 px per step.
- The room, movement and HUD are pure modules in `src/world/`: `shedRoom.ts` (room size, props at their halved `rm_shed` positions, edge walls 2 px thick, thinner than the clamp margin, so the clamp holds the player in at the edges as in Step_0 and wall collision is for interior walls), `player.ts` (`stepPlayer`: input clamped to -1..1, normalised above length 1, per-axis wall collision, clamp, facing with the 0.5 thresholds, the 0.14 walk-animation counter), `input.ts` (keys to input, the touch joystick, the fixed 60 Hz `fixedSteps` accumulator, at most 5 steps a frame), `keys.ts` (`onKeyDown`, through which every scene registers its keydown shortcuts: Phaser 4.2.1 re-emits its whole key queue, up to a frame old, on each new DOM key event, so a handler runs once per event object and one Escape cannot both close a panel and leave the room) and `hud.ts` (the badge text, e.g. `Spring 1/28  |  Day 0  |  $100`; the raw day is shown, as in the prototype).
- Placeholder art: the floor (the room's background colour), walls and labelled props are Phaser rectangles and monospace text; the player is a 16x24 rectangle with its origin at its feet, depth-sorted by y against the props' bottom edges.
- Input: arrows and WASD through Phaser's keyboard plugin, without key capture. On touch (or a mouse), pressing anywhere on the canvas except a button sets a joystick origin; the drag gives the input, with a 4 px dead zone, saturating at 24 px.
- The viewer opens from the room with V (a keydown event) or the `View tree (V)` button, on the first tree in `state.trees` (or the `?tree=` fixture; the inspector's View in 3D opens it on the inspected tree) in `seasonForDay(state.day)` (or `?season=`). While it is open the world ignores its keys and pointers, does not step and hides the HUD; the viewer's Escape and Exit close it and the world resumes.
- The HUD menu: a `Menu` text button at the top-left (the toast sits to its right) opens a panel under it, a stroked rectangle with **Save (F5)**, **Load (F9)**, **Settings** and **Title (Esc)**. Each row does what its key does: Save calls the same save as F5, Load the same reload as F9 (both then close the panel), Title starts the title with the data Escape passes. Settings (no key; the row is its control) opens the Settings panel as a modal (`panel` `settings`), closed by Escape or Close. A press anywhere outside the panel and the button closes it and starts no joystick; the panel's background is interactive, so a press on it never does either. While it is open Escape closes the panel instead of leaving. The button is hidden while the viewer is open, and opening the viewer closes the panel; the open panel is never persisted. Layout numbers (badge, View tree and Notebook buttons, Menu button, toast, panel and rows) live in the pure `src/world/menu.ts` (`menuItems()`), unit-tested to stay inside the room and clear of the badge and the View tree button. `Notebook (J)` sits beside `View tree (V)` at the bottom-left, the tap control for J; like Menu it is hidden under the viewer and under a modal panel.
- The tutorial corner panel (the controller's Draw_64; pure model `tutorialPanel(step, modalOpen)` in `src/world/tutorialPanel.ts`): HUD parts at HUD depth, top-right under the carry line (190 wide at (282, 28): the prototype's 340 at 16 from the right and 32 down, halved, then widened and lowered so the longest step label fits at 8 px and the `Carrying:` line stays clear), shown in every room while `state.tutorialStep` is not done and hidden under the viewer (the prototype moved it to the bottom-right there; this build hides the HUD instead). It stays drawn under an open modal panel (dimmed with the room), with its Skip greyed and not a control, so a press meant for the modal can never skip. Heading `Tutorial`, `tutorialStepLabel`, `tutorialStepBody` wrapped with `wrapLines` (36 characters a line; the box's height follows the line count, so it is pure and tested rather than measured), then `Press J for notebook` and a `Skip` button. The scene redraws it at the start of every publish whose model differs from the one drawn (an action through the sim, a load, the viewer's training, a modal opening or closing), and drops it when the step reaches done. Skip opens the **Skip Tutorial?** confirmation (obj_ui_tutorial_skip_confirm; `skipConfirmPanel()`, its own centred 300x110 box) with the prototype's two lines verbatim, wrapped, and `Cancel` (closes) and `Skip` (`tutorialSkip(state)`, closes) on the line of `Close (Esc)`.
- Granny's notebook (obj_ui_notebook; pure model `notebookPanel(state, page)` in `src/world/notebook.ts`, its own centred 440x220 box): J (through `onKeyDown`) toggles it as the controller's Step_0 did, closing it when it is the open panel and opening it only while no modal is up and the viewer is closed. Pages are `tutorialAllSteps()` plus the finale (`TUTORIAL_DONE`) once the tutorial is done; it opens on the active step's page, or the finale when done. A page shows its title (`tutorialStepLabel`, or `All caught up`) with `Page i / n` on the right of the same line, the badge from `tutorialStepStatus` (`done`, `in progress`, `not yet`), then `Granny left this page blank for now.` on a page not yet reached, else `tutorialStepFlavour` wrapped at 68 characters, `Quick prompt:` and the indented body; the finale shows only its flavour. `< Prev` and `Next >` share Close's line and are greyed (not controls) on the first and last page; each reopens the notebook on the new page, kept as scene state and never saved. ### How the viewer is shaped

- A separate WebGL canvas (`#viewer`) sits fixed over the Phaser canvas and is shown only while the viewer is open.
- The camera is plain yaw/pitch/distance data in the pure `camera.ts`; the world is z-up, as in the prototype.
- Handedness: the prototype's look-at was left-handed, so the viewer mirrors the world's y axis (`toViewerSpace` in `camera.ts`, a y-flipped mesh group in `TreeViewer.ts`). Screen-right at yaw 45 is world (-1,-1,0), as in the prototype. Hotspot projection goes through the same helper.
- Rendering is on demand (one frame per open, resize or input change), never a loop, without MSAA, so a still view is a deterministic screenshot.
- Pure array builders (`potGeometry.ts`) feed Three.js `BufferGeometry`, so mesh shape is unit-tested in Node. `threeCamera.ts` uses only Three's math classes and is unit-tested too; only `TreeViewer.ts` needs WebGL.
- The tree mesh comes from the pure `treeMesh.ts`, which reads shape only from `trunkFrames`, `branchPoint` and the `*FrameAt` lookups. `TreeViewer.ts` keeps it as one `Mesh` in the mirrored group beside the pot and rebuilds it before a render only when `tree.revision` has changed since the last build.
- Wire is part of the bark mesh, as in the prototype: right after a wired branch's bark, `treeMesh.ts` appends a copper helix around the branch and a 1.5-turn anchor wrap around the trunk at its base, ending on the branch's side. Every sample takes its frame from `branchFrameAt` or `trunkFrameAt`, so the coil follows the bent branch and the anchor a leaning trunk, and each tube ring is an oriented ring perpendicular to the helix tangent. Gauge and pitch scale with branch girth and bend.
- Foliage comes from the pure `foliageMesh.ts`: a seeded cluster of crossed, textured quads at each branch tip above 30% of trunk height, tinted by the species' seasonal colour through the vertex colour. The seed is `tree.id * 1000 + branch.id` (mulberry32 in `seededRandom.ts`), so rebuilds never reroll the leaves. `TreeViewer.ts` draws it as a second `Mesh` with its own material (sprite map, alpha test 0.5, no culling).
- The season is an input, never derived: `open(tree, season, state)` and `setSeason(season)`. The viewer reads the game state's day only for wire-age captions, never for the season. Foliage rebuilds before a render when `tree.revision` or the season differs from what it was built with; bark rebuilds on `revision` only.
- Colour space: the renderer outputs `LinearSRGBColorSpace` so palette bytes pass through untouched, and the foliage sprite (`foliage.png`, the prototype's `spr_foliage` copied byte for byte) loads with `NoColorSpace`, nearest filtering and no mipmaps for the same reason. The map is bound when it finishes loading; `foliageReady` on the test hook says when.
- Interaction state is plain data in the pure `hotspots.ts`: mode (`view`, `wire`, `clip`, `prune`, keys V/W/C/P), wire action, bend direction and the wired/unwired filters, reset on every `open`. `hotspotWorldPoints(tree, ui)` gives the hotspots for that state in world space (branch ones at 70% along each branch, trunk ones at 20-80% of the trunk in wire + bend) with the prototype's filters, labels and colours. Nothing in it mutates the tree.
- Hotspots are a DOM overlay (`#viewer-hotspots`, one `button.hotspot` each), not drawn in WebGL: tests read their positions from the hook and the DOM, they get hover and focus for free, and `e2e/screenshot.css` hides them so baselines stay the WebGL frame. `TreeViewer.ts` lays them out again after every rendered frame, so they follow the camera. Each button's hit circle is the prototype's 16 px radius. The overlay sits above the canvas, so a press on a hotspot never starts a camera drag.
- Clicking a hotspot acts through `src/sim/training.ts`: clip mode calls `clipBranch(tree, state, id, 1)`, prune mode `pruneBranch`, wire + bend `applyWire` with the targets from `branchBendTarget` (one 15 degree step on `bend` for left/right or `bendV` for up/down, its sign from `branchBendSign` with the hotspots' own projection), and a trunk hotspot `wireTrunk` at `t * trunk height` toward `trunkBendWorldAngle(bendDir, yaw)`. Wire + remove opens the confirmation (`#viewer-modal`: the pure `modal.ts` holds the prototype's sizes, colours and strings, `ViewerModal.ts` draws it); its Remove calls `removeWire`. While it is open its dim takes every pointer event, the toolbar and hotspots are inert, Escape closes the modal (not the viewer) and other keys do nothing. Hotspot clicks are ignored while a frame is pending, so a second click before the buttons are rebuilt cannot hit a branch a prune just renumbered. Apart from `state.paused` (below), the viewer never writes the tree or state itself: the sim functions do, consuming wire from the inventory and refusing when there is none (the help line then reads `(out)`); a successful action bumps `tree.revision`, so the next frame rebuilds the mesh and the toolbar.
- The toolbar is DOM too: `#viewer-toolbar` (tree info, View/Wire/Clip/Prune and Exit buttons, and in wire mode the action, bend-direction and show sub-row) and `#viewer-help` (the bottom help lines, with the wire stock in wire mode). The pure `toolbar.ts` builds a plain-data model from the tree, interaction state, wire stock and day, holds the prototype's sizes, colours and strings, and gives the wire-age caption under wired hotspots; `ViewerToolbar.ts` draws it after every frame (skipping an unchanged model) and reports clicks to `TreeViewer`'s setters and `close()`. `open(tree, season, state)` takes the `GameState` so it can read the wire stock and day and pass it to the training functions. Mode and camera keys ignore Ctrl, Meta and Alt chords; Escape closes the viewer unless the confirmation is open.
- The viewer pauses the simulation, as the prototype did with `global.game_paused`: `open` sets `state.paused = true` (only once WebGL is available) and `close` (Escape, the Exit button, or the owner) sets it back to false on the state it was opened with. `advanceDayAllTrees` is a no-op while paused. The flag is transient: `serializeState` never writes it and every load starts unpaused. `paused` on the test hook mirrors it.
- `projection.ts` maps a world point to CSS px with Three's math classes only (unit-tested in Node). It goes through `toViewerSpace`, as the handedness rule demands, and drops points behind the camera or outside the near/far range.
- The top strip (60 px, 110 px in wire mode, the prototype's toolbar and wire sub-row) never starts a drag; on a phone the DOM toolbar wraps taller and takes the press itself. Wheel zoom works anywhere over the canvas; pinch zoom wherever the first finger could start a drag; the camera buttons wherever they are drawn.
- Pinch zoom: `pinchZoom(camAtPinchStart, startPx, nowPx)` in `camera.ts` moves `distance` by the change in finger distance over `PINCH_PX_PER_NOTCH` (20 px) wheel steps, continuously, clamped to the wheel's limits, and never touches yaw, pitch or target. `TreeViewer.ts` tracks the pointers down on the canvas: one starts a drag (below the top strip, as before); a second landing during the drag ends it and starts a pinch from the camera at that moment; moves during the pinch only zoom; lifting either finger ends the pinch, and the finger left down needs a new press to drag. A third finger is ignored. Opening the confirmation or closing the viewer cancels a drag or pinch.
- Camera buttons (`#viewer-camera`, built once by `ViewerToolbar.ts`): zoom in (`+`), zoom out (`−`) and reset (`R`), a column at the right edge, vertically centred, sized by `CAMERA_BUTTON_SIZE` (36), `CAMERA_BUTTON_GAP` (8) and `CAMERA_BUTTONS_RIGHT` (20) in `toolbar.ts`. Zoom is one wheel step (`zoomCamera` by -1 or +1), reset is `resetCamera`, as the wheel and R. Inert with the toolbar under the confirmation; hidden by `e2e/screenshot.css` so baselines stay the WebGL frame.
- On a viewport narrower than `SUBROW_ONE_LINE_WIDTH` (830 px, the bend sub-row on one line at the prototype's 24 px group separator) the sub-row's groups sit `SUBROW_SEPARATOR_NARROW` (12 px) apart (`subRowSeparator(viewportWidth)` in `toolbar.ts`), so a phone in landscape (824 px wide) keeps the wire toolbar at 110 px instead of wrapping over the top of the tree. Exit sits in the mode buttons' flex flow (16 px after Prune, as before), so on a narrow phone in portrait it wraps beside Prune rather than taking a row of its own. Branch hotspots stack above trunk hotspots, so where the two overlap on a short viewport a tap takes the branch. The help lines and the modal are unchanged at every size; the S22 Ultra (`s22-portrait`, `s22-landscape`) shows the tree and the whole pot between them in every mode.
- The direction helpers `trunkBendWorldAngle` (screen direction to a world bend angle at the current yaw) and `branchBendSign` (which bend sign moves a branch tip the chosen way on screen, found by projecting a perturbed copy) are pure and take the projector as an argument; the wire actions use them.
- Screenshot tests open fixture trees (`viewerFixtures.ts`, grown through `src/sim` actions) with a `?tree=<cutting|bent|cascade|maple|wired|fancy>` URL parameter, and choose the viewer's season with `?season=<spring|summer|autumn|winter>` (default: the game's season), both read by the boot scene; the tests start a new game from the title with Enter and open the viewer with V in the world. The parameters stay until R4's interactables give a real way to pick a tree.
- Screenshot baselines live in `e2e/__screenshots__/` and are regenerated on Linux with `npx playwright test --update-snapshots=all`.

## Invariants carried over

These were the hard-won rules of the prototype. Each names where it will live in the web project.

- **The tree model is the single source of truth.** 2D sprite and 3D mesh both derive from it. No display state stored separately from morphology. (`src/sim/tree.ts`)
- **Real units.** Trunk height in cm, girth in mm. Scaling for display happens in the viewer only. (`src/sim/`, `src/viewer/`)
- **Scoring is derived, never persisted.** Recompute on demand from morphology, style and vitality. (`src/sim/scoring.ts`)
- **Species and styles are data.** Keyed records, looked up by key; trees store the key. (`src/sim/species.ts`, `src/sim/styles.ts`)
- **Seasons are a pure function of the game day.** 28-day seasons, year starts in spring on day 1, nothing persisted. A new game starts on day 0 as the prototype did; `seasonForDay` treats it as day 1. (`src/sim/seasons.ts`)
- **All growth goes through the season multipliers.** `seasonGrowthMultiplier` returns 0 for dormancy; any path that adds height or girth must consult it. Fertilising refuses when it is 0. (`src/sim/seasons.ts`, `src/sim/growth.ts`)
- **Trunk and branch shape come from one curve helper each**, shared by the mesh builder, hotspot UI and style scorers, so what you see is what you score. (`src/sim/geometry.ts`)
- **Mesh rebuilds are triggered by a revision counter** bumped by every morphology mutation. (`tree.revision`, read by `src/viewer/`)
- **Consumables are really consumed.** Wire, fertiliser and pots are decremented by the action that uses them, gated on availability. (`src/sim/inventory.ts`)
- **Fertiliser is timed.** The item is consumed; the effect lives on the tree until a day threshold. (`src/sim/growth.ts`)
- **Location is a tagged string**, not an enum: a room name, `inventory`, `sold`, or `displayed:<pedestal-key>`. (`src/sim/tree.ts`)
- **Tutorial state is one step counter** advanced idempotently from gameplay call sites. (`src/sim/tutorial.ts`)
- **The 3D viewer pauses the simulation.** `state.paused` (the prototype's `global.game_paused`) is true while the viewer is open; the day advance does nothing while it is. Transient, never saved. (`src/sim/world.ts`, `src/viewer/TreeViewer.ts`)
- **Saves carry a version** and old shapes migrate forward. Prototype saves import one way. (`src/sim/save.ts`)

## Build, test, deploy

- **Gates** (`npm run check`, mirrored in `.github/workflows/ci.yml`): ESLint strict type-checked, Prettier, `tsc --noEmit`, Vitest with coverage, Vite build, then Playwright against the built output in four profiles: `chromium` (desktop Chrome, 1280 x 720), `mobile` (Pixel 7, portrait), and `s22-portrait` and `s22-landscape` (Drew's Samsung Galaxy S22 Ultra in Chrome at its default FHD+ display mode: 384 x 824 and 824 x 384 CSS px at scale factor 2.8125). `e2e/orientation.spec.ts` turns 384 x 824 to 824 x 384 at runtime and checks the world canvas refits and the viewer re-renders without a reload.
- **Tap parity.** The browser tests drive the game through `e2e/drive.ts`. On the S22 projects (`tapRoute: true`) it reaches every action through its visible control by touch; elsewhere through its key or a click. So the suite proves tap parity on the phone and keeps the shortcuts tested on desktop. Gestures (drags, pinch) are the same everywhere; movement keys and the few tests of key handling itself stay keys on every project.
- **PWA.** `vite-plugin-pwa` generates the manifest and a Workbox service worker that precaches the build. The precache size cap is raised because Phaser alone exceeds the default.
- **Hosting.** Azure Static Web Apps. `public/staticwebapp.config.json` sets SPA fallback, security headers and cache policy. `.github/workflows/deploy-swa.yml` deploys `main` to production and each PR to a preview environment, and removes the preview on close. The deploy token lives in a repository secret; without it the workflow verifies the build and skips.
- **Security.** Gitleaks on every push and PR; CodeQL via the repository's default setup; Dependabot for npm and Actions, grouped weekly.

## Known rough edges

- The world is a placeholder shed and garden: rectangles for art. The title starts a real new game or continues a save, the days pass in real time, you can walk around and between the rooms, save with F5, carry trees between the floor and the display pedestals, take juniper cuttings in the garden and plant them at the planting table, and V opens the fully interactive 3D viewer on the first tree in the state (or a `?tree=` fixture). The shop kiosk sells supplies and the workbench makes pots from clay.
- Prototype rough edges (cuttings for junipers only, fancy pots stat-only) carry over until the relevant backlog items are built.
